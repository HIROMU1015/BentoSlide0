# BentoSlide project router

At the start of every task, read `START_HERE.md`, `deck.yaml`, and `python -m scripts.deck_workflow status --json`. Treat `deck.yaml` as the sole machine-readable workflow state, then read the stage-specific rules in `workflow/WORKFLOW.md` and only the relevant specifications.

## Non-negotiable rules

- Infer routine paths, section/chapter selection, state transitions, logs, validation, preview, and conversion commands from the repository. Do not ask the user to repeat mechanical instructions.
- Use the manifest-listed primary sources as factual authority. Do not invent claims, conditions, symbols, signs, subscripts, assumptions, numbers, comparisons, or generalizations.
- For a GitHub repository source, use the connected GitHub App/Plugin only to inspect, search, and select relevant files. Before planning, use `capture-github-source` to resolve the requested ref to one commit and transactionally register its selected tracked bytes and descriptor. Never use moving branch content or connector snippets as authoritative input, never copy app credentials into Git, and never ask the user for source IDs or manifest mechanics. See `docs/github-repository-sources.md`.
- Evaluate every slide for whether a diagram improves understanding. Prefer editable native text/shape/connector diagrams; bind source-derived native components through one assetless `figureId`, and bind every origin-bearing image to its registry `contentDigest`. Distinguish source-original, source-derived, and generated visuals through the registry. Never generate data, experimental/benchmark results, quantitative plots, or equations. Use the transactional visual-asset/PDF extraction route in `docs/visual-workflow.md`.
- For schema v2 `single`/`imported` authoring, `deck/deck.preview.html` and `deck/deck.registry.json` are the pre-conversion visual/provenance source of truth. Migrated `modular` decks retain paired chapter files.
- After conversion, generated artifacts are reproducible and read-only. During `bento_authoring`, authoring HTML/JSON/registry are authoritative. After content approval and final handoff, final `#bento-doc`, frozen final registry, and immutable baselines are authoritative.
- Never write Bento HTML/JSON/registry directly. Use the revision-checked Work editor API or the common transaction/storage layer. Never expose a partially replaced artifact set.
- Work editor authoring may change content and structure, but in-place existing `id`/`type` changes require explicit replacement. Finalization permits only geometry/presentation style/theme/background/z-order changes.
- If a user asks for content or structure changes during finalization/complete, route back through `reopen-current-section`, edit the authoring canonical section, re-accept sections, and obtain a fresh whole-deck approval. Before restarting finalization, stop the final editor and archive the complete previous final/baseline set through the dedicated transaction; never relax finalization protection, edit final content in place, or discard the old final silently.
- Use `python -m scripts.apply_bento_final_edits` only in finalization. Never use it for content or structure. Never reconvert over final, automatically reset final, or use `--allow-content-edit` for ordinary final adjustment.
- Preserve the Bento runtime, synchronous HTML-string `window.bento.serialize()` contract, resource/fallback rules, and legacy JSON-first behavior.
- When conversion exposes a converter defect, use the isolated conversion-repair runner before editing implementation code. Preserve every reported issue, the failed input/evidence, and an exact-slide reproducer when possible; fix the converter rather than weakening canonical HTML to hide the defect. Re-run the affected fixture and selected tests during repair, then run one cache-disabled formal build and the full suite at handoff. Repair cache/status are never approval evidence or source of truth.
- Run the static HTML annotation preflight before Chromium conversion. Treat duplicate identity, unstable explicit fallback, annotation placement, and protected-element coverage as blocking safety errors. Surface nested annotations, text-bearing shapes/groups, and explicit image fallbacks as editability warnings; do not silently claim their text remains independently editable.
- Update state only through `scripts.deck_workflow`. Respect plan, section/chapter visual, Bento content-revision, and final approval gates. On a resolved blocker, run `resume`; never repair YAML fields manually.
- Write planning Markdown and the optional visual plan through the planning artifact writer, not by replacing reviewed files directly. Plan submission stores one signature over the request, source manifest and source bytes, planning files, visual plan, authoring mode/strategy, and ordered sections/chapters. Plan approval must recompute that signature and reject any drift; a planning update invalidates the pending review and returns it to planning.
- A content approval is valid only for the current authoring document and registry revisions. Recompute it on status and every relevant transition or mutation; stale approval is pending.
- A final approval is valid only for the exact final document, HTML, registry, and runtime revisions. Stop the editor before approval; use `reopen-finalization` before any later edit.
- Keep unregistered equations, charts, tables, source-backed media, and `unprovenancedDraft` elements in authoring only. Reject them at content review until their required registry IDs and provenance are complete.
- Server writers hold the OS-level artifact lease for their lifetime. Offline writers must acquire the same lease or use a positively identified matching localhost API; otherwise refuse.
- Recover unfinished transaction journals before serving reads or writes. A report-only failure keeps committed artifacts and is retried; unsafe recovery changes nothing.
- Never mutate generated/final during segment import or targeted replacement. Treat imported HTML as untrusted and preview only sanitized static output.

## Natural-language routing

Natural conversation is the primary UX. Infer routine mechanics, stop at the next human checkpoint, and describe slides by title rather than internal ID. Never require a stage name, revision, registry field, file path, or CLI command. Persist a substantive new brief with `capture-request`. `advance` never records approval.

For new schema v2 single/imported decks, the default is `authoring.strategy: whole_deck`: create the complete fixed-size HTML/registry deck, show one whole-deck preview, then revise it conversationally. Opening review records an immutable checkpoint for HTML, registry, complete deck evidence, and every local dependency. Do not edit reviewed canonical HTML or shared CSS/assets directly. Build a temporary candidate, calculate requested/changed/related slides plus structural, registry, dependency, and global-style impact, tell the user exactly what will change and what else must be rechecked, and ask whether that candidate is acceptable. Only an explicit confirmation in chat or through the revision-bound preview action may approve and transactionally apply the exact candidate; the approval digest also binds the human explanation and base/candidate dependency manifests. Preview slide marks are a review checklist, never independent approvals or partial applies. Reject stale candidates or changed impact evidence, and revalidate canonical/candidate inputs plus dependencies under one union writer lease at apply. After applying, close candidate comparison, show only the updated canonical HTML, browser-check every affected slide that remains in the deck for transformed visible bounds, text-bearing element overflow, visual consistency, and narrative continuity, persist revision-bound report/environment/screenshot evidence, and require a separate current whole-deck HTML approval before conversion.

Persist preview `未確認` / `確認済み` / `要修正` marks and each saved per-slide correction through the workflow API as proposal-ID/digest-bound feedback; do not rely on browser-only storage. When the user says only `修正して` during an active review, read every current saved instruction from status, treat them as the accumulated editorial request, and never ask the user to repeat them. A correction-less legacy `要修正` mark is incomplete input and must be completed in preview first. Reassess the whole story, then use the feedback-digest-bound `revise-html-slide-change` for an agreed local/related scope or `revise-html-change` after explaining structural/global scope. The revision transaction composes from the active candidate, compares the result with canonical HTML, archives the consumed feedback with the superseded proposal, and installs the replacement proposal only after all inputs still match. Do not cancel first or lose an active candidate on generation failure. If the strict localized analyzer detects structure, shared style, registry expansion, or any unexplained newly affected slide, stop and explain the wider scope before using the full candidate route. Local generation never means partial approval, partial apply, or partial formal conversion.

Treat every slide-specific correction as an editorial request against the complete deck, not as an instruction to freeze every other slide. Before drafting a candidate, inspect the whole current story and explicitly assess prerequisites, adjacent transitions, repetition, terminology, numbering/cross-references, conclusions, slide order/count, and section boundaries. Classify the recommendation as local, related, or structural/global. If local, say that no wider change is recommended. If related, include the necessary related slides in the candidate and explain why. If a materially broader reorder, addition/removal, section split/merge, or story rewrite would produce a better deck, propose that direction and its affected slides before building it; do not silently broaden the request or silently settle for a weaker local patch. When the user supplies corrections one slide at a time, reassess the accumulated effect on the whole deck each time. A new instruction for an active proposal amends the pending intent through the atomic revision route instead of stacking an independent edit or cancelling the only reviewable candidate first. The user may explicitly require a strictly local change, but the agent must still disclose any resulting narrative inconsistency.

Sections remain internal planning, provenance, digest, and impact scopes; they are not separate user checkpoints in whole-deck mode. Keep `rolling_sections` only as an explicit compatibility/special-purpose route. In that route, promotion converts only the approved section, preserves planning order, and leaves unrelated authoring slide hashes plus generated/final artifacts unchanged. Accepted sections remain reopenable and whole-deck content review remains mandatory.

The former fixed phrases remain compatibility aliases only. Their exact checkpoint behavior is documented in `docs/legacy-command-aliases.md`; do not present them as the primary UX.

Legacy schema v1 decks must be dry-run migrated with `deck_workflow migrate`; never move a late-stage deck back to Bento authoring merely because of migration.

See `START_HERE.md`, `workflow/WORKFLOW.md`, `docs/source-of-truth-policy.md`, `docs/authoring-lifecycle.md`, and `docs/artifact-transactions.md`.
