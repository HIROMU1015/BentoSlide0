# Slide plan — BentoSlide0を実際に使う

## Section 1: promise

### Slide 1 — この資料そのものが、BentoSlide0のデモ

- 左にリポジトリ内の説明文書、中央に今回のChatGPT Workとの会話、右にBento editorで開いた本資料を置く。
- 主文は「説明している手順で、この資料自体を作る」。
- 「通常は利用者が置いたPDFなどが一次資料。今回はリポジトリ自身が一次資料」と小さく添える。
- `self-demonstrating / local / editable` を短く示す。
- 下段に全体の操作地図として `準備 → 依頼 → 構成確認 → section制作 → 全体確認 → 最終調整 → 完成` を置く。

### Slide 2 — 利用者が最初にすること

- 4枚のstep card：リポジトリを資料ごとに複製／一次資料を `sources/private/` へ置く／必要なら手持ち画像を `images/user/` へ置く／ChatGPT Workでこのプロジェクトを開いて希望を伝える。
- 各cardに、folderや画面の簡潔なUI mockと完了状態を示す。
- 今回だけは、最初から入っている使い方文書を一次資料として参照していると補足する。
- 操作帯：すること「資料を置く」／見ること「対象ファイルが入っている」／伝えること「この資料でスライドを作りたい」。

## Section 2: request-and-plan

### Slide 3 — 最初の依頼は、普段の言葉でよい

- 依頼の型を5つの短い入力欄で示す：目的／想定読者／分量／残したい要素／強調したい点。
- 実例の吹き出し：「このリポジトリの使い方を、初めての人向けの9枚のデモ資料にして。通常の作り方から完成後の直し方まで、操作例を中心に見せたい」
- 右側に、依頼と一次資料が制作の起点として保存される様子を小さく示す。
- 「通常の案件なら、ここに論文・PDF・既存資料が入る」と短く対比する。
- 操作帯：すること「希望を普段の言葉で伝える」／見ること「依頼が正しく理解されたか」／伝えること「不足条件や優先順位」。
- journey barは「依頼」を強調。

### Slide 4 — 最初に確認するのは構成案

- ChatGPT Workが返す説明方針、story、slide planを3枚のcardで示す。
- 確認checklist：事実に誤りがないか／順序が分かりやすいか／枚数と情報量が適切か／図にしたい箇所が含まれるか。
- 利用者の返答例：「結論を先に」「方法は2枚に」「この図は原図を使いたい」「この構成で進めて」。
- 「承認前に勝手に制作を完了しない」を安心材料として示す。
- 操作帯：すること「構成を読む」／見ること「抜け・順序・分量・図」／伝えること「修正点または、この構成で進めて」。
- journey barは「計画」を強調。

## Section 3: section-work

### Slide 5 — 1 sectionずつ、見て・言って・触って・確定する

- 横方向の4場面：HTML previewで内容・読み順・図を見る／自然文で直す／Bentoで文章や図・slide構造を編集／sectionを確定。
- 各場面に見るポイントを置く：初見で意味が通るか／文字量は適切か／図が主張を助けるか／出典が必要な要素は正しいか。
- 発話例：「2枚目の図を大きく」「説明を1行減らす」「この表現を専門外向けに」「ここはこの内容でOK」。
- 全体一括のやり直しではなく、対象sectionだけを更新することを補足。
- 操作帯：すること「画面を見てフィードバック」／見ること「内容・順序・図・出典」／伝えること「具体的な場所と直したい結果」。
- journey barは「section制作」を強調。

### Slide 6 — 開く入口は同じ。画面は現在位置で変わる

- `start_deck_workspace.cmd`を入口として中央に置き、ダブルクリック→clipboardのURLを開く→HTML preview／Bento authoring editor／final editor／完成版viewerのいずれかが表示される流れをUI mockで示す。
- 4画面それぞれに「この画面でできること」を1行で付ける。
- 利用者がstage、port、出力ファイルを選ばないことを明記。
- 内部では`deck.yaml`が現在位置を一元管理する、と小さく示す。
- 操作帯：すること「同じlauncherを開く」／見ること「表示された画面の役割」／伝えること「画面を見た感想や修正」。
- journey barは「section制作」を継続。

## Section 4: approval-and-final

### Slide 7 — 内容を確定してから、見た目を仕上げる

- 左半分にBento authoring：文章、数式、図表、slide構造。
- 右半分にfinalization：位置、サイズ、style、背景、重なり。
- 中央に資料全体の内容確認checkpointを置く。
- 全体確認checklist：事実の誤り／抜け・重複／slide間の流れ／表記の統一。
- 発話例を対比する：内容「3枚目の説明を修正して」／見た目「全体の余白を揃えて、タイトル位置を整えて」。
- 「finalで内容を直接書き換えない」ことを、制限ではなく保護として説明。
- 操作帯：すること「内容を確定してから見た目を確認」／見ること「内容か見た目か」／伝えること「修正の目的と対象」。
- journey barは「全体確認→最終調整」を強調。

## Section 5: revision-and-summary

### Slide 8 — 完成後の修正にも、戻り道がある

- 2分岐：見た目だけなら「5枚目の図を少し右へ」→finalization再開／内容なら「3枚目の説明を更新」→該当sectionへ戻り、再確認後に新finalへ。
- 内容修正中も旧finalは保持され、切替時には旧finalとbaselineがarchiveされることを示す。
- generatedを上書きして帳尻を合わせないことを補足。
- 操作帯：すること「直したい内容を普通に伝える」／見ること「内容変更か見た目変更か」／伝えること「対象と期待する結果」。
- journey barは「完成後の修正」を強調。

### Slide 9 — 覚えるのは、資料を置く・話す・節目で確認する

- すぐ使える最短checklistとして、`複製する → 資料を置く → 希望を話す → 構成を確認 → sectionごとに確認 → 全体内容を確認 → 見た目を仕上げる` を再提示する。
- 中央に3つの大きな動詞「置く・話す・確認する」を置く。
- 下段に「裏側では source of truth / approval / revision / transaction が守る」を小さく配置。
- 最後の一文：「BentoSlide0は、変換器ではなく、完成まで戻れる共同制作workflow」。
- 「そして、この資料自体がそのworkflowで作られた」と示し、1枚目の自己実証visualへ呼応して閉じる。

## 共通レイアウト

- Slide 3〜8の下端に `依頼 → 計画 → section制作 → 全体確認 → 最終調整 → 完成後の修正` を固定表示する。
- 現在位置だけ青緑、利用者の承認箇所はオレンジのdiamondで示す。
- Slide 2〜8に `すること／見ること／伝えること` の操作帯を同じ位置・同じ配色で置く。
- 技術用語は本文より小さな「裏側」cardに限定し、利用者の操作と混ぜない。
